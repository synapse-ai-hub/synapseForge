## 1. Arquitectura y Flujo General del Orquestador

El orquestador maneja la conversación a través de etapas especializadas que transforman el lenguaje natural en acciones técnicas y, finalmente, en una respuesta validada.

### Etapa 1: Router (LLM0) - El Portero del Sistema

El Router es el primer punto de contacto. Su función es clasificar la intención y determinar la ruta más eficiente.

- **Prompt Principal (p_llm_0_router_v2.md)**: Analiza el mensaje para asignar una de las 11 rutas (ej. direct, planner, scraping_linkedin, rag) y detecta el pipeline_mode (prospecting, recruiting o null)

- **Flujo Success**: Si la intención es clara, devuelve un JSON con la ruta y el modo de pipeline

- **Flujo Error/Ambiguo**: Si no puede determinar la intención, activa la ruta clarify, pidiendo información adicional al usuario antes de proceder

**Bypass:**
- **Direct**: Si la consulta es un saludo o conocimiento general, se responde directamente saltando el resto de las etapas técnicas
- **Help**: Consultas sobre la plataforma Syni van directo a una respuesta de ayuda

---

### Etapa 2: Planner (LLM1) - El Estratega

Solo se invoca si el Router determina que la solicitud requiere combinar múltiples herramientas o si el flujo es complejo.

- **Prompt Principal (p_llm_1_planner.md)**: Su misión es recolectar datos, nunca integrar o sintetizar. Crea un plan detallado paso a paso asignando herramientas específicas a cada uno.

- **Flujo Success**: Genera un array de pasos (plan) donde cada paso tiene una description y una tool

- **Flujo Error (Feedback Loop)**: Si pasos anteriores fallaron, el orquestador le pasa las plans_corrections para que el Planner ajuste la estrategia y no repita el error

**Bypass**: Si la solicitud se puede resolver con una sola herramienta, el Router puede enviarla directamente al Decision Maker, omitiendo al Planner para reducir latencia

---

### Etapa 3: Decision Maker (LLM2) - El Traductor Técnico

Toma la descripción de un paso del plan (o la consulta directa si hubo bypass del Planner) y la convierte en parámetros ejecutables.

- **Prompt Principal (p_llm_2_decision_maker.md)**: Extrae parámetros como URLs, ubicaciones o queries cortas estilo Google

- **Flujo Success**: Devuelve un JSON con tool_name y el objeto parameters listo para ser inyectado en el código

- **Flujo Error**: Si faltan parámetros obligatorios, devuelve un estado de error que puede forzar un paso de clarify o un re-intento de planificación

---

### Etapa 4: Executor (Tools) - La Capa de Acción

Aquí se ejecutan las funciones de Python que interactúan con APIs externas (LinkedIn), bases de datos SQL o el motor de búsqueda web.

- **Flujo Success**: La herramienta completa su tarea y devuelve los datos crudos

- **Flujo Canceled/Error**: El sistema monitorea eventos de cancelación (stream_cancel_event). Si la herramienta falla (ej. error de scraping), el error se captura para ser analizado por el Validador

---

### Etapa 5: Validator (LLM4) - El Control de Calidad

Recibe el resultado de la ejecución y lo compara con lo que el paso del plan originalmente pedía.

- **Prompt Principal (p_llm_4_validator_v2.md)**: Decide si el resultado es Valid o Invalid basándose en la utilidad sustancial del dato, no en la perfección técnica

- **Flujo Success (Valid)**: Transfiere el contenido de la herramienta al campo output para que el usuario o el siguiente paso lo utilicen

- **Flujo Error (Invalid)**: Si el resultado es irrelevante o está vacío, genera una correction detallada explicando qué falló. Este feedback se envía de vuelta al orquestador para un posible re-intento o ajuste del plan

**Bypass**: Ciertas herramientas de consulta interna muy simples o respuestas de ayuda pueden configurarse para omitir la validación estricta y pasar directo a la síntesis final.

## 2. Contratos de las Herramientas

Todas las herramientas integradas en la clase Tools siguen un contrato de salida estandarizado para que el orquestador y el validador puedan procesarlas de forma uniforme. El formato exacto es un objeto JSON (o dict en Python) con la siguiente estructura:

| Campo | Tipo | Descripción |
|-------|------|-------------|
| **status** | string | "success" si la herramienta se ejecutó sin errores técnicos; "error" si hubo una falla en la API, DB o scraping |
| **message** | string | Una descripción legible de lo ocurrido (ej. "Herramienta seleccionada correctamente" o "Error al conectar con la base de datos") |
| **data** | object | Objeto que varía según la herramienta |
| **data.reasoning** | string | Breve explicación del LLM sobre la ejecución |
| **data.output / data.result** | object | Los datos reales encontrados (perfiles de LinkedIn, contenido de búsqueda web, registros de DB, etc.) |
| **data.correction** | string | (Solo en caso de error) Feedback para el re-intento |
| **usage** | object | (Opcional en algunas herramientas) Información sobre el consumo de tokens (prompt, completion, total) y tiempo de ejecución |

## 3. Análisis de Puntos de Bypass y Rutas Especiales

El flujo de Synapse no es rígido; se adapta según la ruta detectada por el Router para optimizar recursos.

### Bypass de Respuesta Directa (direct)

- **Ruta**: Router -> Fin
- **Caso**: Saludos ("Hola"), preguntas filosóficas o de conocimiento general que no requieren herramientas externas

### Bypass de Planificación (single tool bypass)

- **Ruta**: Router -> Decision Maker -> Executor -> Validator -> Síntesis
- **Caso**: Si el usuario pide algo atómico como "Buscá perfiles de CTO en Madrid", el Router identifica scraping_linkedin como la herramienta única y el sistema omite al Planner

### Bypass de Validación (Consultas Internas)

- **Ruta**: Router -> Executor -> Síntesis
- **Caso**: Consultas de ayuda (help) o de contexto propio (query_context) donde el resultado es determinístico y no requiere una evaluación de calidad por un LLM adicional

### Bypass de Memoria y RAG

- **Regla Crítica**: Si se menciona un nombre de persona, el sistema hace un bypass de la herramienta rag y utiliza obligatoriamente search_profile_by_name para buscar en la base de datos vectorial de perfiles, evitando confusiones con la memoria de conversaciones

### Bypass de URL Directa

- **Ruta**: Router -> search_profile
- **Caso**: Si se proporciona una URL de LinkedIn, se bypassan todas las búsquedas masivas y se va directo a la extracción del perfil específico

## 4. Resumen del Movimiento de la Conversación

La conversación se mueve de forma lineal-validada:

1. **Clasificación** (Router)
2. **Estrategia** (Planner)
3. **Parametrización** (Decision Maker)
4. **Ejecución** (Tools)
5. **Control de Calidad** (Validator)

Si el Validator aprueba, se avanza al siguiente paso o a la respuesta final. Si desaprueba, se activa el bucle de corrección basado en el feedback generado en el JSON de error.

Este diseño permite que el orquestador sea resiliente ante fallas (mediante el bucle de validación y corrección) y eficiente (mediante atajos inteligentes en conversaciones simples).

---

## 5. Rutas Especiales Adicionales

### Ruta clarify

- Si la solicitud es ambigua o falta información crítica (como el canal o el tono para un mensaje), el orquestador detiene el flujo y pide aclaraciones al usuario

### Ruta special_message

- Flujo optimizado para redactar mensajes de contacto. Si falta el canal (email/LinkedIn/WhatsApp) o el tono (formal/casual), se deriva a clarify

### Ruta query_context vs query_database

- Si el usuario pide recordar acuerdos o conversaciones, usa rag
- Si necesita datos estructurados de la base de datos, usa query_database

## 6. Observabilidad y Debugging

### 6.1 Generación de Seguimiento y Observabilidad (DEBUG)

La observabilidad en Synapse no depende de un único archivo de registro, sino de un contrato de salida estandarizado que cada agente y herramienta debe cumplir para garantizar la trazabilidad total del flujo.

**Identificadores de Rastreo (_debug_id)**: El sistema utiliza el parámetro _debug_id que se propaga a través de las funciones de las herramientas. Esto permite vincular ejecuciones técnicas específicas con la solicitud original en entornos concurrentes.

**Campos de Razonamiento (reasoning)**: Es obligatorio que todos los agentes (Router, Planner, Decision Maker y Validator) incluyan un campo reasoning en sus respuestas JSON:
- El Router aporta una frase corta sobre la intención detectada
- El Planner genera un resumen de por qué eligió ciertas herramientas y el modo de negocio detectado
- El Decision Maker justifica técnicamente la extracción de parámetros

**Métricas de Uso (usage)**: Las herramientas registran opcionalmente información sobre el consumo de tokens (prompt, completion, total) y el tiempo de ejecución. Por ejemplo, ciertas herramientas miden explícitamente el tiempo de inicio para calcular el rendimiento.

**Marcadores de Código Estandarizados**: Internamente, el código utiliza etiquetas como ### DEBUG, ### FIXME, ### REVIEW y ### NOTE para gestionar el estado de depuración y las decisiones técnicas no obvias durante el desarrollo.

---

### 6.2 Generación de Prompts Dinámicos por Herramienta

La arquitectura de Synapse genera prompts en tiempo de ejecución mediante la inyección de variables en plantillas estructurales (archivos.md).

**El Rol del Decision Maker (LLM2)**: Este agente actúa como el "traductor técnico". Su prompt se construye dinámicamente al recibir:
- La Descripción del paso generada por el Planner
- El Nombre de la herramienta asignada
- Ejemplos de la Herramienta (tool_examples): Se inyectan esquemas y ejemplos específicos para que el modelo sepa exactamente qué parámetros extraer

**Propagación de Datos Críticos**: Existe una regla estricta para el Planner: si el usuario proporciona una URL, el Planner debe incluirla de forma literal en la descripción del paso. Esto garantiza que el prompt del Decision Maker contenga la información necesaria para que la herramienta final pueda ejecutarse; de lo contrario, el sistema fallaría por falta de parámetros.

**Adaptación de Búsqueda**: Para herramientas de búsqueda web, el prompt instruye dinámicamente que la query sea "estilo Google" (corta y con palabras clave). En otras herramientas, se inyectan listas de categorías válidas para que el modelo mapee la solicitud del usuario a categorías entendibles por la API.

### 6.3 Prompt Engineering vs. Context Engineering en Synapse

En esta arquitectura, ambos conceptos se utilizan de forma sinérgica para lograr un comportamiento equilibrado entre reglas fijas y adaptabilidad.

| Característica | Prompt Engineering (Estructural) | Context Engineering (Situacional) |
|----------------|-----------------------------------|-----------------------------------|
| **Ubicación** | Archivos.md (instrucciones base) | Marcadores {variable} inyectados en runtime |
| **Función** | Establece el rol, tono, reglas críticas y formato (JSON) | Aporta la materia prima para la decisión del momento |
| **Uso en Synapse** | Definir que el Validator no debe evaluar cantidad de resultados, sino utilidad | Inyectar la Memoria del Usuario, la Fecha actual y el Historial de interacción |
| **Resiliencia** | Reglas de "no inventar datos" y "rechazar en caso de duda" | Inyección de plans_corrections y results_corrections cuando un paso previo falló |

**Evaluación de lo que se está usando**: Synapse utiliza Prompt Engineering para crear la "Constitución" del sistema (por ejemplo, prohibiendo revelar información interna o definiendo los niveles de Recall y Precision del validador).

Sin embargo, el sistema depende críticamente de la Ingeniería de Contexto para su funcionamiento inteligente. La capacidad del orquestador de pasar la "Salida validada de pasos anteriores" (validated_output) al siguiente agente es lo que permite que el sistema tenga una memoria de trabajo coherente durante una ejecución compleja. Además, el uso de feedback loops (donde un error del validador se convierte en una instrucción de corrección para el planner) es una forma avanzada de ingeniería de contexto que dota al sistema de autorreflexión y resiliencia.

## 7. Gestión de Modelos (LLM vs SLM)

En la arquitectura de Synapse, la gestión de modelos se basa en una estrategia de especialización y jerarquía, donde se distribuyen las tareas entre modelos de lenguaje grandes (LLM) y modelos más pequeños o especializados (SLM / modelos de nicho) para optimizar la precisión, el costo y la latencia.

### 7.1 Modelos de Lenguaje Grandes (LLMs)

Estos modelos se encargan de la orquestación, el razonamiento estratégico y el control de calidad.

**Router (LLM0) – El "Portero"**: Clasifica la intención del usuario entre 11 rutas posibles y detecta el contexto de negocio (pipeline_mode). Se utiliza un LLM aquí porque requiere entender matices del lenguaje natural para decidir si una solicitud es ambigua, un saludo o una tarea técnica compleja.

**Planner (LLM1) – El "Estratega"**: Solo se invoca para solicitudes complejas. Su misión es desglosar la consulta en un plan de pasos secuenciales. Requiere una capacidad de razonamiento superior para asignar las herramientas correctas y manejar bucles de retroalimentación si un plan anterior falló.

**Decision Maker (LLM2) – El "Traductor Técnico"**: Traduce descripciones en lenguaje natural a parámetros técnicos específicos (JSON). Se utiliza un LLM para asegurar que la extracción de entidades (como URLs o nombres) sea precisa y cumpla con el esquema de la herramienta asignada.

**Validator (LLM4) – El "Control de Calidad"**: Evalúa si el resultado de una ejecución cumple con lo solicitado en el plan. Se emplean diferentes niveles de validación (estricta vs. media) según la necesidad de precisión (Precision) o recuperación (Recall) del flujo.

**LLM Final (Síntesis)**: Se encarga de integrar, comparar y sintetizar todos los resultados recolectados antes de dar la respuesta al usuario.

### 7.2 Modelos Pequeños y Especializados (SLMs y Embeddings)

Estos modelos se utilizan para tareas de bajo nivel, procesamiento de datos masivos y búsquedas específicas, donde un LLM generalista sería ineficiente.

**SentenceTransformer (Embeddings)**: Se utiliza para la gestión de la base de datos vectorial y el almacenamiento de perfiles. Este tipo de modelo transforma texto en vectores numéricos para permitir búsquedas semánticas eficientes.

**"LLM Pequeño" (Reranking)**: En la herramienta de búsqueda de perfiles, después de que la búsqueda semántica trae candidatos, se utiliza un "LLM pequeño" para elegir el mejor match entre los resultados. Esto ahorra recursos al no usar el modelo principal para una tarea de selección simple.

**Modelo de Búsqueda Especializado**: La herramienta de búsqueda web utiliza un "modelo especializado con capacidades de búsqueda". Este modelo está optimizado para navegar por internet, extraer información de múltiples fuentes y sintetizarla rápidamente.

### 7.3 Justificación de la Selección (¿Por qué cada uno?)

La elección entre un modelo u otro responde a cuatro criterios fundamentales:

**Reducción de Latencia (Bypass)**: El sistema está diseñado para saltarse etapas complejas (y modelos pesados) mediante rutas de bypass. Por ejemplo, si la consulta es un saludo, el Router envía la respuesta directamente, evitando invocar al Planner o al Validator.

**Precisión mediante Descomposición**: Al separar el "razonamiento de planificación" (LLM1) del "razonamiento de validación" (LLM4), el sistema evita sesgos. El Validador tiene prohibido evaluar criterios técnicos que no estaban en el plan original, actuando como un auditor independiente.

**Eficiencia en RAG**: El sistema combina la búsqueda semántica (SLM) con un filtrado por relevancia posterior mediante un LLM, asegurando que solo la información más útil llegue a la síntesis final.

**Resiliencia y Aprendizaje Contextual**: El uso de LLMs en las etapas de planificación permite procesar las plans_corrections (feedback de errores previos). Esto permite que el sistema "aprenda" de una falla técnica en la misma sesión y ajuste su estrategia dinámicamente.
